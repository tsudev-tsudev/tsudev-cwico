# Session 2026-08-19-01

**Started:** an empty directory containing three files - a 640-line PowerShell
script (`Optimize_Win11_For_Dev.ps1`), a batch launcher, and `tsudev-logo.png`.
No git repository, no `STATE.md` (this system did not exist yet).

**Goal:** turn the script into a professional Windows debloater with a real
safety model, a GUI, packaging, and a published repository.

## What happened

### Choosing the stack

The host has Rust 1.97, Node 22 and Python, but **no .NET SDK**, and WPF/WinUI
cannot be built on Linux at all. That ruled out the otherwise-obvious C#/WinUI
option: it would have meant writing several thousand lines that could not be
compiled, let alone tested, until they reached a Windows machine.

Rust + Tauri v2 was chosen instead. The decisive property was not binary size
or cross-platform reach - it was that `cargo check --target
x86_64-pc-windows-gnu` type-checks the entire Windows backend from Linux, and
that the safety logic could be put in a crate with no OS calls whose tests run
anywhere.

### The architecture that fell out of that

`cwico-core` makes no operating-system calls at all. Everything that decides
whether an action is safe - classification, the planning gate, the deletion
guard - lives there, which is why 128 tests including the adversarial ones run
on a Linux CI runner in under a second. `cwico-win` is adapters. The Tauri
layer is transport. A bug in the UI cannot talk the engine into doing
something dangerous because the UI does not get a say.

Three modules inside `cwico-win` were deliberately kept host-independent
(`cmdline`, `naming`, `protected`) after the first round of testing showed
that `UninstallString` parsing is where the subtle bugs live. Moving them out
from behind `#[cfg(windows)]` turned two latent production bugs into failing
tests within a minute - see *Problems found*.

### The safety model

Built in three independent layers, on the assumption that any one of them will
eventually have a hole:

1. `data/safety-db.json`, 58 rules. Unmatched items resolve to `Unknown`,
   never `Safe`. When an item matches both a `Safe` and a `Critical` rule,
   `Critical` wins - severity beats specificity.
2. `RemovalPlan::build` refuses to plan `Critical` items at all, and requires
   an explicit per-item acknowledgement for `Caution` and `Unknown`.
3. `guard::validate_delete_path` / `validate_delete_key` vet every target
   immediately before deletion.

The test that matters most is
`selecting_everything_still_cannot_remove_a_critical_component`: it ticks
every row, confirms every prompt, presses go, and asserts Defender and RPC
survive.

### Verification approach

Because none of this could be run on Windows, verification was layered:

* `cargo test` for the engine (128 tests)
* `cargo check --target x86_64-pc-windows-gnu` for the Windows backend
* headless Chromium screenshots of the real built UI, which is how the
  service deep-clean bug below was found
* CI on a Windows runner - the first time the code was compiled by MSVC
* the release workflow run manually, which is the only thing that exercises
  `cargo tauri build`

Each layer caught something the previous one could not.

### Publishing

Repository created at `tsudev-tsudev/tsudev-cwico`, 15 commits. CI green
across four jobs. The release workflow was run manually three times; the
artefacts were downloaded and inspected (`file` reports a genuine WiX 3.14
MSI, a real NSIS PE32, and a PE32+ console binary).

## Decisions

**Rust + Tauri over C#/WinUI.** See above. The deciding factor was
verifiability from this host, not the technology's merits in the abstract.

**`cwico-core` makes no OS calls.** This is a constraint, not an
observation - adding a `#[cfg(windows)]` to that crate means the logic belongs
somewhere else. It is what makes the safety layer testable.

**Services are disabled, never deleted.** A service's registry key *is* the
service. `Uninstall` on a service means stop and set `StartType = Disabled`,
which is one call to undo.

**`Critical` is absolute.** No flag, CLI switch or confirmation dialog removes
a `Critical` item. `assert_no_protected_items` re-checks the invariant
immediately before execution so that a future refactor reintroducing the hole
aborts the run rather than proceeding.

**Rule labels do not rename items.** An early version let a rule's `label`
replace the item's `DisplayName`, which turned "Candy Crush Saga" into
"Preinstalled third-party games & trials" in the list - hiding the very thing
the user came to remove. Labels are now grouping metadata only.

**`--name` matches at word boundaries.** Plain substring matching meant
`--name Edge` also selected "Acme L**edge**r Desktop". For a destructive
command that is not a usability wrinkle, it is a way to remove software the
user never asked about.

**Documentation numbers are CI-enforced.** `tools/check_docs.py` cross-checks
the rule counts, tweak count and MSRV quoted in the READMEs against the actual
data files. "58 safety rules" would otherwise outlive the 59th rule.

## Problems found

Listed because each one was found by a *different* verification layer, which
is the argument for having all of them.

| Problem | Found by | Consequence if shipped |
|---|---|---|
| `Uninstall.exe` (NSIS) matched `starts_with("unins")` and was classified Inno Setup | moving the parser to a host-independent module so its tests ran | NSIS uninstallers given `/VERYSILENT`, which they ignore - a window opens during a "silent" removal |
| Unquoted `UninstallString` containing spaces split at the first space | same | `C:\Program Files\App\unins000.exe` launched as `C:\Program` |
| Deep clean on a service targeted `HKLM\…\Services\<name>` | reading the plan dialog in a UI screenshot | the service *definition* deleted rather than disabled - unrecoverable without a reinstall |
| `beforeBuildCommand` used `../../ui` | the manual release run | `cargo tauri build` fails; `cargo build` does not invoke the hook, so CI's Windows job passed regardless |
| No `vite-env.d.ts` | a Dependabot TypeScript bump | TypeScript ≥6 rejects `import "./index.css"` outright |
| `cargo test --workspace` pulls in the Tauri crate | running the command this project's own README recommended | the documented test command fails on any machine without webkit2gtk |
| GitHub strips inline `style` from Markdown | re-reading the branding requirement | the two-colour wordmark rendered as plain grey text on every page of the repository |
| winget manifest generated `PackageVersion: main` | reading the generated file instead of trusting the green tick | a manifest pointing at `/download/vmain/` |

The last two are worth dwelling on: both were produced by code that had just
run successfully. A green check mark means the command exited zero, not that
it did the right thing.

## Left undone

* **Nothing has run on a live Windows machine.** This is the single largest
  gap. Every Win32 and WinRT call compiles and every pure function is tested,
  but no code path has touched a real registry or service control manager.
* Installers are unsigned; SmartScreen will warn.
* Microsoft Store submission and winget publication both need accounts and a
  tagged release.
* Linux and macOS backends are unwritten - the `PlatformBackend` trait is the
  seam they would plug into.
