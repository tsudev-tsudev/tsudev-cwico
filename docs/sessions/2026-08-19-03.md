# Session 2026-08-19-03

**Started:** commit `188e0bb`, version 1.0.0, everything green but nothing
released.

**Goal:** answer whether GitHub Releases can carry this project at zero cost,
then cut the first release, submit to winget, and prepare the SignPath
application.

## What happened

### The zero-cost question

Verified from documentation rather than memory, because the answer drives a
spending decision:

* GitHub Actions is free and unlimited for **public** repositories, all runner
  types including Windows. Private repos get 2,000 minutes/month and Windows
  costs a multiple of that, so *keep the repository public* is a real
  constraint, not a preference.
* Release assets have no bandwidth limit and no total-size limit; individual
  files cap at 2 GiB against our 3.6 MB.

So the entire pipeline is $0. The only cost was code signing — and that turned
out to have a free path too.

### A correction to my own earlier documentation

`docs/SIGNING.md` said an Authenticode certificate has to be bought. That is
wrong for an open-source project: the [SignPath
Foundation](https://signpath.org/) issues them free to qualifying ones, and
this project meets the substantive conditions. Writing "buy a certificate"
would have cost the maintainer money for nothing.

While checking, a more serious point surfaced: **SmartScreen reputation for an
unsigned binary is tracked per file hash.** This project ships on a date-based
schedule, so an unsigned build never accumulates enough reputation before it
is superseded — the warning is permanent rather than a first-release
inconvenience. That is now the stated reason to sign, ahead of any single
warning.

### Cutting the release

Four attempts, because each one exposed something the previous verification
had not.

1. **Tagged, built, drafted.** Then I downloaded `latest.json` and read it:
   `"notes": ""`. The mandatory update dialog would have blocked users with no
   explanation of what they were being made to install — the one thing that
   makes a forced update defensible. The release body was empty because
   nothing passed one. Fixed by extracting the CHANGELOG section
   (`tools/changelog_section.py`), with a missing section failing the build.
2. **Re-tagged.** Then I realised the notes are Markdown and the dialog renders
   plain text — users would read the explanation through stray `>`, `###` and
   backticks. Fixed with a small formatter rather than a Markdown renderer.
3. Feeding the fixture realistic Markdown immediately exposed a third bug: a
   wrapped bullet became its own paragraph, so a sentence split mid-thought.
4. **Re-tagged again**, verified, published.

The published endpoint now returns HTTP 200 with version `26.8.1901`, three
platform entries and 4,982 characters of notes, and both payload signatures
verify against the key compiled into the application.

### winget

Submitted as
[microsoft/winget-pkgs#420321](https://github.com/microsoft/winget-pkgs/pull/420321).

The generated manifest had a bug worth recording: the download URL was built
from the *version* (`.../download/v26.8.1901/`) where the *tag*
(`.../download/tsudev-cwico-v26.8.19/`) belongs. It 404s. The manifest looked
perfectly well-formed and would have gone to someone else's repository that
way. `tools/apply_winget_manifest.py` now downloads the installer and checks
both the URL and the hash before writing anything.

The manifests were also three years of schema revisions behind — 1.6.0 against
the 1.12.0 their checklist asks for — which only surfaced from reading their
pull request template rather than assuming.

## Decisions

**Two checklist boxes left unchecked on the winget PR.** `winget validate` and
`winget install` cannot be run from this host. Ticking them would have been
faster and dishonest. The pull request says what *was* verified instead, and
why the boxes are empty.

**The release notes lead with a warning** that this has never run on a live
Windows machine, and point at the three commands that change nothing.
Publishing a debloater that has only ever been compiled deserves that more
than it deserves a clean announcement.

**SignPath deferred** by the maintainer: internal testing first. The
application text and the required public policy are written and committed, so
submitting later is filling in a form rather than reconstructing an argument.

## Problems found

| Problem | Found by |
|---|---|
| `latest.json` carried empty notes | Downloading and reading the artefact instead of trusting a green pipeline |
| Release notes rendered as raw Markdown in the dialog | Realising where the text ends up |
| Wrapped bullets split into separate paragraphs | Feeding the fixture realistic Markdown rather than clean prose |
| winget download URL built from the version, not the tag | Reading the generated manifest field by field |
| winget manifests on schema 1.6.0, not 1.12.0 | Reading their PR template instead of assuming |

Every one of these was produced by a pipeline that had just reported success.

## Left undone

* **The CLA on winget#420321.** Microsoft's bot requires the account owner to
  sign it; nothing in that pull request proceeds until then, and their
  validation does not run beforehand.
* **Still nothing has run on a live Windows machine.** The release makes this
  more pressing, not less: there is now a binary people can download.
* **The update path has never been exercised end to end.** It needs two
  published releases — install `v26.8.19`, publish a second, watch the gate
  appear and the installer hand over. The UI states and the signatures are
  verified; the handoff to the Windows installer is not.
* SignPath application, deferred deliberately.
